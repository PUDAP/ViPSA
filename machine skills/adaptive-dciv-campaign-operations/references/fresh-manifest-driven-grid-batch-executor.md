# Fresh manifest-driven batch executor after hard-coded launchers

Use when the operator authorizes a new batch but existing launchers are device-specific and contain stale identity, source pose, target coordinates, cap, or point-count assertions. Missing generic launchers are a software implementation task, not grounds to run a stale launcher or request redundant hardware authorization.

1. Preserve optimizer recipes and manifest bytes. Verify source hashes, canonical recipe digest encoding (e.g. sorted compact JSON excluding only recipe_sha256), all binding fields, explicit operator order and authoritative absolute grid targets. Explicit grid order supersedes default serpentine.
2. Generate fresh batch-scoped common/navigation/electrical/supervisor modules in a durable namespace; don't blindly substitute device numbers in old scripts. Existing SDK primitives may be reused read-only. Write and exercise offline failing tests first. Verify all recipes' actual compiler arrays and native point counts, not only syntax.
3. Use the existing global controller flock, not a new batch-only lock. Enumerate actual Python edge processes by /proc PID CWD and executable (exclude uv/shell wrappers); require one protected edge plus exact loaded deployment hash. Require fresh OFF=0, matrix=nil, empty error queue, REAR and live Stage/Zaber pose agreeing with confirmed/no-pending tracked Stage state. Preserve before/after raw envelopes.
4. Verify predecessor terminal, last health cleanup, unresolved-operation latch and source pose. Audit target occupancy across execution namespaces. Journal every move INTENT durably before dispatch; matched success plus exact readback changes it to COMPLETE. An exception leaves UNKNOWN and forbids replay. Completed travel followed by a capture failure is not permission to repeat travel.
5. Probe the exact camera URL before lighting. Capture fresh nominal geometry, inspect physical apex and selected pad, derive bounded corrections, journal them, recapture and inspect. Use substrate-only phase correlation with Hanning to quantify SAME-pad displacement, excluding the probe; save source/after hashes, target, residual overlay, live pose and reviewed alignment-verified.json. Optical alignment is not contact proof.
6. BEFORE pre-approach, execute real fixed preparation constructors, all SDK compile_operation calls and mapping/qualify checks. Otherwise a missing template key or stale mapping may fail only after a +40 motion. Qualify current energy authorization separately; preserve sampled-energy accounting.
7. Preparation uses the campaign's existing forming/conditioning physics. Forming three consecutive qualifying points means outbound POINTS within one sweep, not three sweeps. Persist pre-approach and subsequent motion intents. Carry preparation sweep health cadence; never replay a claimed preparation after a crash.
8. Construct the actual candidate initial_ledger from verified preparation terminal bytes/hash and exact immutable IDs before native dispatch. A continuous 10-cycle native request needs batch-aware validation of every ordered segment/row and actual proof shape, rather than an old single-sweep validator. Persist the full raw reply BEFORE parsing so post-acquisition exceptions do not lose evidence.
9. Energy attribution is one continuous timeline: first rectangle once at batch start; boundary trapezoids once, assigned to the following segment. Do not restart each segment at time zero or charge its first absolute timestamp again. Test partition sums against whole-timeline integration.
10. Latch a qualifying three-cycle failure when encountered after the minimum-cycle boundary, even if a later cycle inside the already-dispatched 10-cycle batch appears to recover. Record first confirmed cycle and full acquired-batch completion separately. Health neither increments cycle count nor resets the failure streak. Cap enforcement must agree in recipe, candidate and supervisor.
11. A bounded per-device worker may retain the global owner and execute sequential candidate batches with cleanup/health at each boundary. An existing continuation cron can perform agent-reviewed next-device navigation/alignment, but must first check the worker PID/cmdline/CWD; while alive it must not send getters, interrupt, modify running source or start a duplicate worker. Stop without replay on UNKNOWN or unresolved INTENT after worker exit.
12. Distinguish preparation complete, native request dispatched/edge received, native result verified, device terminal, and full batch complete. A pending native reply is not a completed cycle, and historical cleanup does not prove OFF during active acquisition. Publish execution acknowledgement beside immutable handoff, with exact operation/run IDs and evidence paths.
