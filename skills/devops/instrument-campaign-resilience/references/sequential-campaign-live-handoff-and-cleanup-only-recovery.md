# Sequential campaign live handoff and cleanup-only recovery

## User-facing workflow correction

Resolve who this session actually is before delegating a live start. A parent must not address its own bot handle as a separate hardware owner or treat an earlier offline-only child assignment as its permanent role after the user explicitly orders execution. A genuinely offline-only child must remain offline. Establish the real exclusive controller/lease, not ownership from a display name. Do not launch a competing controller.

For an authorized continuous campaign, known recipe-specific terminal outcomes plus verified cleanup can permit progression to the next saved physical assignment. Do not repeatedly seek permission already granted or turn reporting/offline future work into routine launch gates. “Remove blockers” never authorizes bypassing collision, native integrity, unknown-exposure, owner, cleanup, preparation-once, or hard-cap checks.

Report actual status concisely: start phase and native run ID from the acquisition journal, or the exact failed check and saved receipt. Offline test success, spawned process, and completed navigation are not electrical acquisition receipts. Distinguish dispatched INTENT from returned measurement data. Reconcile delayed background failures with the current journal; do not mistake superseded launches for the active worker.

## Validated implementation pattern

1. Keep physical-device identity, raw recipe identity, geometry, and preparation/candidate counts independent. Read explicit saved assignments; an exceptional previous assignment does not create a new inferred shift. Derive travel start from a native-verified prior terminal, not a hardcoded previous-device corridor.
2. Test the actual recursive historical validator on real temporary SQLite and the production native transport with a fake connector. Include exact historical stopped operations, recovery suffixes, the new current reservation, and full navigation-to-worker integration. Mocking `store.validate` hides the crucial post-reservation failure.
3. An executor's own current INTENT may be recognized only by the same owner/journal lease and a private token prepared before reservation, bound after durable exact plan/scope insertion. An old INTENT cannot be adopted. Wrong scope, stale token, unrelated uncertainty, duplicate commands, and incomplete native responses remain blockers.
4. A failed launch may dispatch successful output-OFF and matrix-open cleanup even when it sends no motion or electrical stress. Classify that as cleanup-only hardware dispatch—not zero dispatch. Audit event grammar, matched native request/reply/lifecycle identities, complete inventory, and independent unchanged-pose/OFF/open/error readbacks.
5. For a proven cleanup-only stop, preserve original STOPPED_NO_REPLAY row/events. Record a separate, real evidence-reviewed recovery disposition for that exact stopped device; bind it to evidence hashes, current user authorization, distinct retry identity, fresh readiness and exact plan/scope. Another device's administrative approval is not this recovery approval. Reserve the distinct retry additively; reject duplicates and further retry after uncertainty.
6. Recursively validate the preserved history plus completed retry when advancing to subsequent normal devices. Test retained-history mutation, missing/wrong disposition, uncertain motion, skipped physical order, stale readiness, native timeout before XY, and duplicate replay rejection.
7. If a legacy forming worker hardcodes the original navigation key, use an isolated module namespace/instance-local hook to the reviewed navigation-clear validator. Preserve original compiler/electrical operations and all shared historical sources. Verify full recipe parameter parity before actual stress; do not globally monkeypatch the worker or owner scope.

## Strict readiness receipt construction

Where validation expects `load(receipt) == {k:v for k,v in context.items() if k != 'readiness_evidence'}`:

- Remove any inherited/template `readiness_evidence` before writing the new receipt.
- Write the complete context itself as the receipt, not a wrapper such as `{context: ..., native_values: ...}`.
- Preserve native wire/value proofs in separate referenced artifacts.
- Hash the written receipt, then add its path/hash to the live context.
- Validate before creating physical claims or dispatching preapproach/stress.
- Preserve rejected artifacts. A corrected pre-dispatch context is not permission to replay any actual exposure.

## Test and delegation discipline

Keep synthetic fixtures, owner locks and temporary SQLite outside the production inventory tree. Test-local relocation of write guards must not modify production guards. Load lazy historical reconcilers before installing test fixture roots when imports initialize shared module globals. Freeze reviewed sources during the suite; source-pin drift is a real failed test, not a pass to reinterpret. Do not blindly repin historical sources.

A timed-out child can leave useful artifacts, but is not a verified deliverable. Inspect its source, pins and logs, then independently exercise the relevant paths. Avoid competing edits when another bot owns the repair. Do not claim a whole suite passed from one corrected test; state combined versus individual results accurately. Keep after-device plotting/count reports separate from progression decisions and preserve all actual forming/preparation/candidate exposures.
