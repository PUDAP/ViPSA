# Clean expiry: health-only continuation and continuous progression

## Exercised boundary

A sequential native campaign completed forming and preparation once, then 50 candidate cycles. Recipe failure was latched at cycle49. The readiness context expired before dispatching the cycle50 health check. All dispatched events were COMPLETE and final cleanup was verified. The original journal retained UNKNOWN_STOP_NO_REPLAY.

The verified recovery audited the original ordered prefix, exact native identities and parameters, raw hashes, inherited counters, energy, claims, and final pose. It created an additive continuation with fresh native readiness and **only the pending health operation**. Fixture tests passed; live execution returned recipe_specific_failure, 50 cumulative cycles, failure latch49, cleanup verified. The original journal hash remained unchanged. No forming, preparation, motion, or candidate cycle was repeated.

## Reusable rules

- A freshness exception is not proof of zero exposure. Prove it happened before the next INTENT; reject any unresolved dispatch.
- Recompute inherited stop status before selecting remaining operations. A latched recipe failure excludes every later candidate batch, even if a pending health read passes.
- Acquire genuinely fresh readiness; do not refresh timestamps on stale acquisition evidence.
- Preserve the original UNKNOWN/error and link it from the new continuation. Audit both histories before next-device progression.
- Returned near-compliance health data is a terminal safety event: never repeat that health read or further stress on that device. Do not charge unaccounted returned exposure as zero.

## Continuous-campaign preference

The user's “Don't stop” correction means perform routine evidence reconciliation and advance through the next saved assignment without asking for another continue message. It does not waive mandatory safety stops, explicit tool approvals, unknown-motion checks, or image review. A background completion event is a continuation trigger, not merely a notification to summarize.

Reports must distinguish process launched, preflight running, and native acquisition started. Require a durable native acquisition identity/receipt before claiming measurements have begun.

## Immutable adapters and checkpoints

Keep historical journals, native acquisition code, claims, and source-pinned adapters unchanged. Build narrowly scoped additive modules; run offline fixture tests before live execution. Freeze all source files before generating a checkpoint that pins them; adding a verification script later can change whole-directory source-pin sets. Exclude mutable whole-navigation-database hashes from stable terminal evidence only when an exact retained operation-row audit replaces that dependency. Preserve recipe arrays, ordered assignments, and exact historical safety exceptions; never introduce a blanket UNKNOWN waiver.

## Receipt helper pitfalls

Some normal receipt validators require state COMPLETE and an absolute output directory. Do not relabel a safety-rejected UNKNOWN event to satisfy the helper. Verify its returned native envelope through an explicit terminal-only audit. Resolve the output directory before passing it to strict raw-path equality checks.

This reference records the completed health-only recovery. It does not certify any later unfinished adapter or promise a generic recovery API.
