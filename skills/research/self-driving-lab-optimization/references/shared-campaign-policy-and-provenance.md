# Shared campaign policy transitions and acquisition provenance

## Validated coordination pattern

1. Read the handoff, then re-read the live shared artifacts. A diagnostic handoff may describe an earlier pose or acquisition while later forming/conditioning or UNKNOWN writes already exist. Do not replay from stale context.
2. Resolve the single executor, original ownership lock, runner, journal, permanent ledger and authoritative request. A shared file or Telegram mention is not evidence of peer receipt or execution.
3. At an owned idle/branch boundary, link a versioned operator authorization. Preserve original recipe/hash provenance, charge history and candidate/device identity. Never reset a budget to apply a waiver.
4. Audit all enforcement layers: controller reservation gate, adapter pre/post-acquisition limits, receipt validator and readiness/request validation. A configuration-only edit may leave hardcoded gates active.
5. Re-read ready/request/recipe before final verification. If another agent publishes an amended request during the work, validate its actual authorization file hash, scope and active-request agreement rather than weakening validators or rewriting the original payload.
6. Exercise software-only execution and targeted tests. Verify ledger/checkpoint/recipe hashes before and after. No new acquisition is needed to validate software policy application.
7. Report software application, owned boundary acknowledgement, hardware dispatch and verified live receipt as separate milestones. Do not claim hot reload of an existing process.

## Scope-specific operator corrections

An explicitly authorized cumulative-energy waiver removes only that campaign/device cumulative stop. Preserve forming/read limits, compliance, existing branch-warning scopes, nonfinite/UNKNOWN stops, cleanup and no-replay handling unless separately changed. Use campaign/device scope checks and reject out-of-scope identifiers. Keep finite cumulative accounting even when the ceiling is disabled.

Initial endurance caps count complete SET/RESET pairs, not write sweeps. A 100-pair cap implies 200 writes before separately counted reads. Survivors at the cap are right-censored, not failed. Report the configured cap rather than a hardcoded previous cap. Later BO caps require a separate batch-review decision. Existing results are not silently rewritten by prospective policy changes.

## Read-only provenance audit

- Compare raw and parsed voltage/current/time/order programmatically; distinguish measured values from command-index metadata.
- A checkout commit, current disk hash or historical PID does not uniquely identify acquisition-time loaded code. Compare release Git objects, saved launcher/deployment records, reload hashes and timestamped module fingerprints tied to the acquisition interval. Do not substitute file modification times for execution proof.
- Missing metadata is missing evidence. Absence of a newly introduced integrity field may be compatible with an older driver, but does not identify it uniquely.
- Relay closure and REAR readbacks establish logical routing only, not cable continuity, electrode polarity or probe contact. An image can show projected alignment/occlusion, not electrical contact or vertical gap.
- Requested ILIM/range/NPLC values are not applied-setting proof without acquisition-time readbacks/errors. Later driver fixes cannot retroactively validate an earlier response.
- Partial native traces retain raw evidence and uncertain exposure. Never use list indices to assert applied-command correspondence for shortened traces, and do not resume automatically.

## Verification cautions

Inherited unittest classes can run the same baseline cases repeatedly. Distinguish test invocations from unique tests. Test cumulative waiver behavior above the old ceiling, unchanged phase ceilings, UNKNOWN/no-replay handling, finite accounting, out-of-scope rejection, immutable request validation and survival censoring. Software-only success is not physical qualification or proof of a new live receipt.
